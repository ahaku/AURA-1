# Building AURA-1

AURA-1 is an app on [fm1-base](https://github.com/charlesvestal/fm1-base) (`base/`, a git submodule, with
felucca-bsp inside it). Clone with `--recursive`, or after cloning:

```
git submodule update --init --recursive
```

`./build.sh` runs fm1-base's build (`base/tools/build.py`) on `app/`, whose settings are in `app/fm1.toml`. It
makes, in `app/build/`:

| File | What |
| --- | --- |
| `aura-1.bin` | the firmware app |
| `loader/ota.bin` | the update loader (felucca-bsp's) |
| `aura-1.fwsc` | the installable package (app + loader) |

## Prerequisites (macOS)

- Python 3.11 or newer with Pillow: `python3 -m pip install -r requirements-ci.txt`
  (Homebrew's Python, with libraqm, for the fonts).
- Docker Desktop, or podman with a `docker` script that runs `exec podman "$@"` first on your PATH. The JieLi
  toolchain is Linux x86-64 only; the build runs it in a `linux/amd64` `debian:bookworm-slim` container
  (Rosetta on Apple silicon). Keep the source tree in a folder the container can share, e.g. under `/Users`.
- The JieLi Linux toolchain (clang 4.0.1 for pi32v2, from JieLi's package server): see fm1-base's README.
- The JieLi AC79 SDK (Apache-2.0). The package uses three of its files (`cpu/wl82/tools/uboot.boot`,
  `cfg_tool.bin`, `cfg/eq_cfg_hw.bin`); none of it is part of this tree or of git.

  ```
  git clone --depth 1 --branch AC79NN_SDK_V1.2.1_2023-12-13 \
      https://gitee.com/Jieli-Tech/fw-AC79_AIoT_SDK.git ~/fw-AC79_AIoT_SDK
  ```

- Emscripten (optional, for the browser builds) and Node.js (optional, for their tests).

On Linux x86-64 the toolchain runs natively and no container is needed.

## Build

```
./build.sh                    # app/build/aura-1.fwsc
./build.sh --release X.Y      # app/build/aura-1-X.Y.fwsc, identity FM-1_7XXYYZZ
./build.sh --host             # the simulator: app/build/host/aura-1_host
./build.sh --web              # the browser emulator: app/build/emu/
web/app/build.sh              # the web app (the engine alone, for phone and desktop): app/build/app/
```

`JIELI_TOOLCHAIN` and `AC79_SDK` override the default locations (`~/.jieli/toolchain`, `~/fw-AC79_AIoT_SDK`),
`PYTHON` the Python that runs the build. The build also checks the image, RAM and pool sizes, that register access
stays in felucca-bsp, and that no double-precision code is linked.

## Previewing the website

The site uses static HTML, CSS and JavaScript generated by Python. With Emscripten
on your PATH, build the emulator and then assemble the landing page, guide and installer:

```sh
./build.sh --web
python3 tools/make_pages.py
python3 tools/check_site.py app/build/pages
python3 tools/serve_site.py --port 8080
```

On Windows, `powershell -ExecutionPolicy Bypass -File tools/make_pages.ps1` builds
the complete site. Open `http://localhost:8080/`; the instrument is at `/emu/`.
The preview server also serves the designed error page with HTTP status 404.

Activate Emscripten first (`emsdk_env.bat`), set `EMSDK`, or pass
`-Emsdk C:\path\to\emsdk`. The script also recognises an `emsdk` checkout next to
this repository. Native command failures stop the script. `tools/build_web.ps1`
only builds and tests the browser targets; `tools/make_pages.ps1` also generates
and checks the site. It uses the bundled firmware by default; pass `-Package`
to preview an installer for another package. Python 3.11 or newer is required.
Pillow also needs FriBiDi (`fribidi.dll` on `PATH`) on Windows; check with
`python -c "from PIL import features; print(features.check('raqm'))"`.
See [Pillow's Windows build instructions](https://pillow.readthedocs.io/en/stable/installation/building-from-source.html).

Set `FM1_SITE_URL` before generating the site to change the canonical URL, sitemap
and social image URL. For a local metadata check, use `http://127.0.0.1:8080/`.
For publishing, set it to the final public URL. Generation and preview never publish.

The browser regression check needs Node.js, Playwright and a Chromium browser.
Install the pinned browser dependencies and run it while the preview server runs:

```sh
npm ci --prefix tests/browser
cd tests/browser
npx playwright install chromium
node ../host/studio_test.mjs http://127.0.0.1:8080/
```

It checks playback, touch controls, guide search, recording, Zen, reduced motion,
offline startup and the installer's read-only UI. It never writes to an FM-1.

## Tests

```
sh tests/run_tests.sh             # AURA-1's
sh base/tests/run_tests.sh        # fm1-base's own
```

AURA-1's: the instrument (`tests/host/amb_test.c`); the update path against `app/build/aura-1.fwsc`; the browser
builds in Node; and the whole app in the simulator (`tests/scenarios/*.amb`: the pieces, the scale, Motion, the
help cards, the screen reader, an AMB-1 0.9 project carried over), with audio and screenshots in
`app/build/scenarios/`.

`app/build/host/aura-1_host SCRIPT OUTDIR` runs one script. The commands are listed at the top of
`base/host/plat_host.c`, and AURA-1's own checks and commands at the top of `app/host.c`.

## Install

From the command line (needs `pip3 install mido python-rtmidi`):

```
python3 base/tools/fm1_install.py app/build/aura-1.fwsc
```

Installing firmware is at your own risk. Hold REC while switching the FM-1 on to enter update mode. OCT− and
OCT+ together at startup open panel calibration instead. If the FM-1 no
longer starts but reaches the chip's update mode (4C4A:8057 on USB), `base/bsp/tools/fm1_rescue.sh` puts stock
firmware back from a Mac.

## Publishing a release

See [PUBLISHING.md](PUBLISHING.md) for the one-time GitHub setup, development
builds, Pages deployment and the public repository checklist.

A release is built on GitHub from its tag, so anyone can check that the package came from this source:
`.github/workflows/release.yml` calls the shared FM-1 builder,
[`zvenson/fm1-build` at `v1`](https://github.com/zvenson/fm1-build/tree/v1) (as LOOM-8, MONK-1, X0X and Melodee do).
The builder checks out the tagged commit, installs JieLi's Linux toolchain and the AC79 SDK at its fixed tag, runs
`./build.sh --release X.Y` (with fm1-base and felucca-bsp at the commits this one links), installs the pinned
Emscripten toolchain for the browser and `.rfm1` builds, and runs `tests/run_tests.sh` (a failing test stops the
release). It then signs build provenance for `aura-1-X.Y.fwsc`, `aura-1-X.Y-app.bin` and `aura-1-X.Y.rfm1`. The Firmware Hub shows such
packages as built from source.

1. Write the notes first, as a draft: `gh release create vX.Y --draft --title "AURA-1 X.Y" --notes-file NOTES.md`
   (the workflow keeps a draft's notes; without one it makes a draft from the commits).
2. Push the tag: `git tag vX.Y && git push origin vX.Y`. The workflow builds, tests, attests, checks the SHA-256 sums
   and the signatures against the builder, the tag and the commit, then publishes the draft. A tag with a suffix
   (`v1.4-beta`) is a prerelease. A published release is never rebuilt: a new build needs a new tag. A manual run
   on a branch (Actions, Run workflow) builds and attests a development package, in the run's `packages` artifact.
3. Download the verified release from the repository's Releases tab. GitHub Pages
   is published separately by `deploy-pages.yml`: it follows `main`, builds a fresh
   development firmware and runs the complete test suite before deployment.
   To preview a release installer locally, download its `.fwsc` and run
   `python3 tools/make_pages.py app/build/aura-1-X.Y.fwsc X.Y`, then
   `python3 tools/check_site.py app/build/pages`. Build the emulator from the same
   release tag first. Publication uses GitHub Actions rather than a `gh-pages` branch.

To check a downloaded package yourself (GitHub CLI, signed in):

```sh
tag=vX.Y repo=ahaku/AURA-1
gh release download "$tag" --repo "$repo" --dir build/verify --pattern '*.fwsc'
git fetch origin "refs/tags/$tag:refs/tags/$tag"
gh attestation verify "build/verify/aura-1-${tag#v}.fwsc" --repo "$repo" \
  --signer-workflow zvenson/fm1-build/.github/workflows/build.yml \
  --source-ref "refs/tags/$tag" --source-digest "$(git rev-parse "$tag^{commit}")"
```

The same checks the `-app.bin`. `SHA256SUMS` comes with the downloads; a checksum alone proves nothing about where a
package was built.

A local release build (`./build.sh --release X.Y`, package `app/build/aura-1-X.Y.fwsc`; its identity FM-1_7XXYYZZ is
what the installer checks) is still how to try one on the FM-1 before tagging.
